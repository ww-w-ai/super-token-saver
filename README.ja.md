# super-token-saver

**CCのソースコードを実際に読み込み、トークンの消費先を特定して自動修正する唯一のClaude Codeプラグイン。コストを減らし、より長くコーディングできる。**

> 実測結果：実際の $326/日 のワークロードで **45% のコスト削減** → $180/日。SubTaskへの自動委譲、ゼロコストでのコンテキスト復元、完全な分析ダッシュボード、そしてキャッシュ期限切れのガード — ゼロ設定で、1回のインストールで完結。

**Max Plan ($200/月)** と **API従量課金** の両方に対応。同一プラグイン、同一機能。すべてのユーザーにとって強力 — トークンが実際のお金になるユーザーには特に。

![使用状況ダッシュボード — トークンの消費先を正確に把握](docs/images/usage-view-overview.png)

### 30秒でわかる機能概要

| ------- | ------------ | ------ |

| 🪶 Concise Mode | レスポンスの冗長な表現を削減し、内容を維持 | 1回のレスポンスあたりの出力トークンを削減 |

## 😤 問題点

**見えないコスト。** リアルタイムの可視性なし。「コンテキストが80万トークンに達しました」という警告なし。「3分前にキャッシュが期限切れになりました」というアラートなし。被害が出てから気づく。

**コンテキストの肥大化。** 同じプロンプトでも、20万トークンのコンテキストと80万トークンのコンテキストでは4倍のコスト差。Read、Grep、Edit のたびにコンテキスト全体が再送信される。1つの複雑なプロンプトで15回以上のAPI呼び出しが発生し、それぞれがコンテキストサイズで乗算される。

**キャッシュの期限切れ。** 昼食から戻ってきたとき、キャッシュが消えている。次のメッセージで90万トークンが通常価格で再送信される。1回で $9。

**すべて手動。** コンテキスト管理、キャッシュ期限切れのタイミング、SubTask委譲、セッションのクリーンアップ。実際にコーディングしながらこれらすべてを追跡できる人はいない。

**Max Plan ($200/月) をお使いの場合？** 上記すべてに加え、タイマーも予定時刻表示もない5時間のレート制限がワークフローを止める。

**API従量課金の場合？** 上記すべてに加え、上限がない。1回のキャッシュミス = $9 の実際のお金。週に10回 = 事故だけで $360/月。コンテキストが肥大化した最悪の火曜日は、Max Planユーザーが1ヶ月に払う金額より高くなる可能性がある。

super-token-saver はこれらすべてを自動的に処理する。**1回インストールするだけ。**

## 🧠 機能1: スマートセッションアーキテクチャ

**インストールするだけで、コスト最適化された作業パターンが自動的に適用される。**

ほとんどのユーザーはメインセッションですべての作業を行う。ファイルの読み込み、コード生成、テスト実行。すべての出力がコンテキストに積み重なり、すべてのメッセージと一緒に再送信される。セッションが肥大化し、コストが雪だるま式に増える。

Session Architect はセッション開始時に委譲戦略を自動的に注入する。

|                  | メインセッション                      | SubTask                               |
| ---------------- | --------------------------------- | ------------------------------------- |
| 役割             | 設計、意思決定、レビュー         | 実装、コード生成、マルチファイル  |
| キャッシュ期間       | 1時間 (ephemeral_1h)             | 5分                                 |
| キャッシュ書き込みコスト | ＄10/MTok                          | ＄6.25/MTok                            |
| コンテキストサイズ     | 平均 ~94K                          | 平均 ~33K                              |

SubTaskのキャッシュ書き込みはメインより **37.5% 安い**。コンテキストサイズも大幅に小さい。重い作業をSubTaskに委譲することでコストが劇的に削減される。

**結果：** コンテキストが600K以上に膨らむ代わりに250K以下に抑えられる。同じ作業量で、トークンコストは半分。完全自動。

## 🪶 Concise Mode

**同じ内容。少ないパディング。デフォルトで有効。**

SessionStartフックは **すべてのセッションとすべてのモデル** で実行されるレスポンススタイルルールも注入する — フラグなし、設定なし。3つの変更が行われる：

- **前置きの削除** — 「確認します…」「では…」、質問の言い換え、diffがすでに示している内容の要約なし
- **内容に適したフォーマット** — リスト向けには箇条書き、推論（トレードオフ、因果関係、根拠）には散文。どちらかを強制しない
- **簡潔な表現** — 同じポイントをより少ない言葉で。明確な散文は短い散文

ハードリミット：内容を省略したり、検証をスキップしたり、ニュアンスを1文にまとめたりしない。内容は完全に維持され、ラッパーだけが縮小される。

1回インストールすれば、すべての場所に適用される。

## 🔄 機能2: /s-continue — コンテキストの復元

**`/compact` の代替。LLM呼び出しゼロ。トークンコストゼロ。情報損失ゼロ。**

`/compact` はコンテキスト全体（約100万トークン）をLLMに送信して3.3%のサマリーに圧縮する。キャッシュが期限切れの場合、それだけでフルキャッシュ再構築が発生する。情報損失は避けられない。

`/s-continue` はまったく異なるアプローチを取る。前のセッションのトランスクリプトを前処理して直接読み込む。LLM呼び出しなし。コストなし。元の会話がそのまま復元される。

|                         | /compact                          | /s-continue                        |
| ----------------------- | --------------------------------- | -------------------------------- |
| 仕組み            | コンテキスト全体をLLMに送信してサマリー作成 | トランスクリプトを前処理して直接読み込み |
| LLM呼び出し               | 必要（通常10万トークン以上） | 0                                |
| トークンコスト              | 高い                              | 0                                |
| 情報損失        | あり（3.3%サマリー）                | なし（元のまま保持）        |
| 処理速度        | 数十秒                   | 1秒以内（60MB以上のファイルでも）       |
| キャッシュ期限切れ時   | 追加でフルキャッシュ再構築コスト発生         | 影響なし                        |
| マルチセッション復元   | 不可                      | 対応済み                        |

使い方：`/clear` してから `/s-continue`。前のセッションのリストが表示される。復元したいものを選択する。素早く回復する場合：`/s-continue last`。

**結果：** ゼロコストで前の作業を再開。情報損失なし。60MB以上のトランスクリプトを1秒以内に処理。

### 🤝 対になる機能：`/s-compact` — 見えないレイヤーを引き継ぐ

`/s-continue` はトランスクリプト — あなたとClaudeが交わした会話 — を復元する。しかし作業セッションで最も有用な知識は、しばしばその対話の外にある：サブエージェントが見つけたこと（そのトランスクリプトは別ファイルで、復元時には読み込まれない）、ツール出力の中の決定的な数字（テスト件数、ベンチマーク値）、作業過程で得た教訓（「ヘッドレスで再現しなかったのはコードではなくビルドの問題だった」）。

セッションの終わりに `/s-compact` を実行すると、まさにこの見えないレイヤーを引き継ぎ記録に凝縮し、`~/.claude/super-token-saver-data/<project>/handoff.md` に保存する。次のセッションでは `/s-continue` が復元したトランスクリプトの上にこれを自動で読み込む — 貼り付け不要。

|                     | `/s-continue` 単独            | `/s-compact` + `/s-continue`（セット）          |
| 復元範囲            | トランスクリプト（交わした会話）  | トランスクリプト＋見えないレイヤー             |
| サブエージェントの発見   | 失われる（別ファイル）           | 引き継ぎ記録に凝縮                       |
| ツール出力の数字 | チャットに引用された場合のみ    | 意図的に抽出                            |
| 作業過程の教訓     | なし                               | 同じ失敗を繰り返さないよう記録              |

**作業の流れ：** セッションを `/s-compact` で終え → 次のセッションを `/s-continue` で始める。

### 🔀 二つのツール、一つの履歴 — Codexのセッションもここで復元できる

Codexはセッションを `~/.codex/sessions/` に、Claude Codeは `~/.claude/projects/` に書き込む。互いに相手のファイルを読まないため、Codexで予算切れになったタスクはClaude Codeから手が届かなかった。逆方向も同じだった。

`/s-continue` は今、両方の履歴を一覧表示し、復元する。Codexのrolloutを別のパーサーに渡すのではなく、Claude Codeが書く形式へと **入力1行につき出力1行** でそのまま書き換える。だから同じパイプラインが両方に対応し、`L{n}` マーカーは元のCodexファイルの正確な行を指し続ける。実測:12 MB、1,540行のrolloutの前処理は **0.13 s**。

|                        | Claude Codeセッション | Codexセッション |
| ---------------------- | ------------------- | ------------- |
| `/s-continue` に表示 | ○ | ○、現在のプロジェクトに限定 |
| LLMコスト0で復元 | ○ | ○ |
| `L{n}` で元の位置へ | ○ | ○ — 行番号はrollout自身のもの |
| コンテキスト消失（`#0`）からの復元 | `/compact`、自動compact | Codexのcompactionとスレッドロールバック |
| `/s-compact` の引き継ぎ | プロジェクト単位で共有 — 片方で書いて、もう片方で読み込む |

```
/s-continue codex                    only Codex sessions
/s-continue codex : rust migration   the turns matching a topic, restored in full
```

正しい一覧と、もっともらしいが間違った一覧を分けるのはこの二点だ。Codexの `session_id` はサブエージェントがそのまま引き継ぐ **スレッド** idなので、セッションは `payload.id` で識別し、サブエージェントのrolloutはClaude Codeがsubtaskのトランスクリプトを除外するのと同じ方法で取り除く。そして `<codex_internal_context source="goal">` はシステムが自動で挿入するものなので、復元後のコンテキストには残るが、ユーザーが打ったターンとしては数えない。

このプラグインはCodexにもインストールされる — **[README-CODEX.md](./README-CODEX.md)**（[한국어](./README-CODEX.ko.md)・[日本語](./README-CODEX.ja.md)・[简体中文](./README-CODEX.zh-Hans.md)）を参照。`usage-view`、`report-limit`、`setup-statusline` は今のところClaude Code専用のまま。

## 📈 使用状況ダッシュボード (/usage-view)

**ついに答えが出る：「そのお金はどこへ消えたのか？」**

Max Planユーザーはレート制限に達して理由を不思議に思う。APIユーザーはAnthropicの請求書を開いて驚く。いずれにせよ、問いは同じ：どのセッションが最もトークンを消費したのか？いつコストが急増したのか？使用パターンはあるのか？これまで — すべて見えなかった。

`/usage-view` はすべてを表示する。インタラクティブなHTMLダッシュボードがブラウザで開き、使用パターンを分析してコストスパイクの根本原因を追跡できる。外部依存関係なし。スタンドアロンで動作。ファイルとして共有可能。

**31日間で $4,196。どこへ消えた？** 一目で — 総コスト、タイプ別のトークン内訳、キャッシュ効率比、セッション数。ドーナツチャートは、支出の65%がキャッシュリード（正常かつ健全）であることを即座に示す：

![使用状況ダッシュボード概要](docs/images/usage-view-overview.png)

**インストール前後の比較 — 推測でなく実測。** オレンジの破線「Plugin installed」マーカーがコストのタイムラインを二分する。日次バーはトークンタイプ（Input/Output/Cache Write/Cache Read）でスタックされ、インストール後にどのコンポーネントが変化したかが正確にわかる。平均ラインがトレンドを示す：

![日次コストトレンド](docs/images/usage-view-daily-trend.png)

**最もコストがかかる時間帯は？** 時間帯別の時間コストと曜日別の内訳。アクティブ日平均、全日平均、最大値の切り替えが可能。炎アイコンが最も高額な時間帯をマーク — 明確なパターン（深夜の集中作業、水曜日のスパイク）が即座に浮かび上がる：

![時間帯別・曜日別コストパターン](docs/images/usage-view-hourly-pattern.png)

**効率は上がっているか？** Total/Output比は、1出力トークンあたりに消費されるトークン数を測定する。低いほど良い。「Plugin installed」マーカーでインストール前後を比較できる。スパイク = キャッシュミスまたはセッションの再起動：

![効率トレンド](docs/images/usage-view-efficiency.png)

**すべてのAPI呼び出しを、コンテキストサイズとコストでプロット。** コスト構造が理解できるチャート。各ドットは1回のAPI呼び出し。赤 = Opus、青 = Sonnet、緑 = Haiku。破線は理論的な価格設定 — ドットが線より上にある場合、過払いしている。**User Turn** ビューに切り替えると、API呼び出しごとではなく会話ターンごとのコストが表示される。
任意のドットにホバーすると、実際のプロンプトテキスト、トークン数、完全なコスト内訳（Input/Output/Cache Write/Cache Read）が表示される：

![コンテキストサイズ別コスト — 散布図](docs/images/usage-view-cost-scatter.png)

**コンテキストのサイズは？** ほとんどの呼び出しは25万以下に集中している。35万以上のロングテールがコストが爆発する領域 — このチャートはどれほど頻繁に危険ゾーンにいるかを正確に示す：

## ✂️ 機能4: /setup-git-lite — CCの組み込みgit指示を削減

**Claude Codeのソースコードを読んだ。毎セッション、あなたが気づかずに払っている2,200個の隠しトークンを発見した。**

### 発見の経緯

2026年4月12日、[GitHubのissue](https://github.com/anthropics/claude-code/issues/47107)により、Claude Codeの組み込み `includeGitInstructions` 設定が毎セッション静かにトークンを消費していることが判明した。[このgist (spilist)](https://gist.github.com/spilist/b0db92a859192f5ec6199d3f35a81b98) による独自の再現で数値が確認された：gitコミット後のセッションごとに**キャッシュ書き込みで +6,031 トークン**、すべてのAPI呼び出しで**キャッシュリードで +1,690 トークン**。

### CCソース分析 — トークンの行方

Claude Codeソース（v2.1.88）の2つの独立した注入ポイントにトークンを追跡した：

**1. `gitStatus` スナップショット（約500トークン） — システムプロンプト**
- `context.ts:36-111` の `getGitStatus()` がブランチ + メインブランチ + user.name + フルステータス（最大2000文字）+ **最近5件のコミット** を収集
- `appendSystemContext`（`utils/api.ts:437`）経由でシステムプロンプトに追記
- 新しいコミット、新しい変更ファイル、ブランチの切り替えのたびにテキストが変化 → プレフィックスキャッシュの無効化

**2. コミット/PRワークフロー指示（約1,700トークン） — Bashツールの説明**
- `tools/BashTool/prompt.ts:53` が60行以上の安全プロトコル、ステップごとのコミット手順、HEREDOCの例、PRの作成テンプレートを `Bash` ツールの説明に追記
- システムプロンプトと一緒にキャッシュされるが、`tools[]` パラメータとして送信される

### なぜ高額なのか

キャッシュ構造（`utils/api.ts:321` `splitSysPromptPrefix`）には、アクティブなMCPツールの有無に基づいて3つのパスがある：

- **パスA**（MCP有効 — ほとんどのユーザー）：`gitStatus` が `cacheScope: 'org'` ブロック内にある。変更が発生すると → 次のセッション開始時にブロック全体が再キャッシュ → 6Kトークンの `cache_create` ミス。
- **パスB**（MCP無効）：`gitStatus` が `cacheScope: null` 動的ブロックに入り、すべてのAPI呼び出しで新鮮な `input_tokens` として再送信される — キャッシュミスはないが、キャッシュの節約もない。
- **パスC**（3Pプロバイダー / 実験的ベータ無効）：パスAと同じ。

通常のインタラクティブセッションでは、コミット/PR指示（1.7Kトークン）が `cache_read` 経由で **すべてのAPI呼び出し** に蓄積される。Opus 4.7の価格設定で100回呼び出しのセッションでは、Claudeのトレーニングがほとんどカバーしている指示に対してだけで約 **$0.08/セッション** となる。

### super-token-saverによる対処法

`/setup-git-lite` はネイティブパスを無効化し、SessionStartフック経由で **280トークンの厳選した代替** を注入する。Claudeのデフォルト動作を上書きするもの（安全ルール）だけを残し、Claudeがトレーニングですでに知っていること（ステップごとのワークフロー、PRテンプレート、ghの使用パターン）はすべて削除した。

**保持 — 11個の重要な上書きルール**（Claudeのデフォルトの親切さを慎重さに変えるもの）：
- 明示的なユーザーの要求なしにコミット/プッシュ/修正/PR/タグ/マージを絶対に行わない
- フックをスキップしない、main/masterへのフォースプッシュをしない、破壊的な操作を実行しない、git設定を変更しない
- `.env`、`credentials`、`*.pem`、`secret.*` に一致するファイルをコミットしない
- `git add -A` / `git add .` を避ける
- 複数行のコミットメッセージには HEREDOC + `Co-Authored-By: Claude` トレーラー
- インタラクティブフラグ（-i）を使わない、空のコミットをしない
- pre-commitフックが失敗した場合 → `--amend` ではなく新しいコミットを作成する

**削除** — ステップごとのコミットワークフロー（3ステップ）、ステップごとのPRワークフロー（3ステップ）、PRのタイトル/本文テンプレート、`gh` コマンドの参照、`-uall` フラグの警告、リベースでの `--no-edit` の警告、`コミット中にTodoWriteまたはAgentツールを絶対に使わない` という制約。これらはClaudeがトレーニングだけで正しく構成できるワークフローの冗長な記述。

**追加** — コンパクトなgit状態行：ブランチ + HEAD短縮sha + 件名 + 現在のステータス（最大20件の変更ファイル、それ以上は件数）。最近のコミットリストなし（Claudeは必要に応じて `git log` を実行できる）。

### 期待される節約（Opus 4.7価格設定、出力$25/MTok、入力$5/MTok、キャッシュリード$0.50/MTok）

| 項目 | 元の状態 | setup-git-lite使用後 | 節約 |
| ---- | -------- | ------------------- | ----- |
| システムプロンプトの読み込み（新規セッションごと） | ~2,200 tok cache_create | ~280 tok cache_create | ~1,920 tok |
| 同一セッション内の繰り返し呼び出し | ~1,700 tok cache_read/呼び出し | ~280 tok cache_read/呼び出し | ~1,420 tok/呼び出し |
| 100回呼び出しセッション（Opus 4.7） | — | — | **~$0.11節約** |
| 1日20セッション × 22就業日 | — | — | **月~$48節約** |

### 使い方

```bash

/setup-git-lite install    # CCネイティブを無効化して最小限のフックを有効化
/setup-git-lite revert     # デフォルトを復元（アグレッシブ；下記参照）
/setup-git-lite dismiss-banner    # 推奨ヒントを非表示にする

```

### インストールの仕組み

`install` は堅牢性のために **2つ** の場所を変更する：

1. `~/.claude/settings.json` — `"includeGitInstructions": false` を追加
2. シェルプロファイル（`~/.zshrc`、`~/.bashrc` など） — `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1` をエクスポートするマーカーブロックを追記

どちらか一方だけでCCネイティブを無効化するには十分だが、環境変数による上書きでネイティブの動作が誤って再有効化されないよう両方を設定する。シェルの変更は新しいシェルでのみ有効になる。

### リバートの仕組み — アグレッシブ

`revert` はシェルプロファイルから **すべての `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS` のエクスポートを削除する**（このスキルをインストールする前に手動で追加したものも含む）。これは意図的 — `revert` を実行したのだから、デフォルトに戻す。シェルプロファイルのタイムスタンプ付きバックアップを必ず先に作成する。

別の理由で環境変数が必要な場合は、`revert` を実行する前にメモしておき、後で再追加する。

### super-token-saverをアンインストールする前に

**先に `/setup-git-lite revert` を実行**すること。そうしないと、settings.jsonには `includeGitInstructions: false` が残るが代替フックがない状態になる（Claudeはgitのガイダンスを全く受け取らない）。Claude Codeには現在プラグインのアンインストールライフサイクルフックがないため、自動化できない。

### トレードオフ

失われるもの（そして通常問題ない理由）：
- セッション開始時にClaudeが事前計算された `git status` / `git log -n 5` を受け取らなくなる。新しいセッションで「何が変わった？」と聞くと、Claudeが自分でコマンドを実行する（余分なツール呼び出し1回、約300トークン）。
- ClaudeがCCの標準的な3ステップコミット手順を受け取らなくなる。数百のコミットフローでのテストでは、トレーニングレベルの知識が重要なケース（HEREDOCフォーマット、`--amend` なし、フォースプッシュなし）を処理できる（これらを明示的なルールとして保持しているため）。
- PRの本文テンプレート（`## Summary` + `## Test plan`）が注入されない。その形式が重要な場合は、プロジェクトの CLAUDE.md に記載する。

### 推奨バナー

CCのネイティブgit指示がまだアクティブな場合、super-token-saverはセッション開始時に **約20%の確率**で1段落のヒントを表示する（`/usage-view` と `/report-limit` の出力にも表示）。`/setup-git-lite dismiss-banner` で恒久的に非表示にできる。

## 🛡️ 機能5: Token Guardian

**キャッシュ期限切れがコストを発生させた瞬間を知らせる。求めれば $9 の再送信をブロックすることもできる。**

Claude Codeのプロンプトキャッシュの有効期間は1時間。それより長く離席すると期限切れになる。次のメッセージでコンテキスト全体が通常価格で再送信される。90万トークンなら、1回で $9。

Token Guardian は最後のレスポンスを受信した時刻を覚えている。3,590秒（TTLから10秒のバッファを引いた値）以上が経過していたら、介入することができる。**デフォルトでオフになっている。Remote Controlがあるからだ。** フックのブロックメッセージはローカルのシステムメッセージとして描画され、リモートのクライアントには届かないため、リモートのユーザーには説明もなくプロンプトが消えたように見えていた。どこで操作しているかによって挙動が変わるガードを出すよりも、オフにすることを選んだ。Remote Controlがフックメッセージを転送するようになれば、デフォルトは再びオンに戻る。それまでは、2つのモードのどちらかで自分でオンにしてほしい。

```
export CC_TOKEN_SAVER_CACHE_GUARD=warn    # Claudeが返信の最初の行で期限切れを伝える
export CC_TOKEN_SAVER_CACHE_GUARD=block   # プロンプトが下記のメッセージとともに一度だけ拒否される
```

`warn` ではプロンプトはそのまま通り、Claudeは返信の冒頭でキャッシュが期限切れだったこと、このターンがコンテキスト全体分として課金されたこと、1時間以上の離席後は `/clear` → `/s-continue` の方が安いことを1行で伝える。これはリモートのクライアントにも届く。フックのメッセージは届かなくても、Claudeの返信は転送されるからだ。

`block` ではプロンプトが下記のメッセージとともに一度だけ拒否される。もう一度送信すれば通る。強制停止が欲しいときはローカルのターミナルで使う。

```
🚨 Cache expired (68m 23s idle)

The prompt cache has expired. Continuing will resend the full context.
Cost may increase significantly.

👉 /context — Check current context usage before deciding
👉 /clear → /s-continue — Reset, then restore previous context (recommended, cheapest)
👉 Re-send — Continue as-is (full re-cache cost incurred)
```

ブロックメッセージはOSのロケールに基づいて23言語で表示され、アイドル期間ごとに1回だけ表示される。

**バックグラウンドエージェントは決してブロックされない。** 検査の対象は人間が直接入力したプロンプトだけだ。バックグラウンドエージェント・タスクの完了報告は — 今や起動から1時間以上経ってから届くのが当たり前になっているが — そのまま素通りするので、長時間動くエージェントの結果が止められたり失われたりすることはない。

**結果：** warnモードでは、$9の再送信がいつ・なぜ起きたのかを常に把握できる。blockモードではそもそも起きない。期限切れを1回ブロックするごとに $9 の節約、1日1回なら月 $270 の純粋な無駄が消える。

> **API従量課金の場合、影響はさらに大きい。** Max Planユーザーは $200 の枠内で $9 を失う。あなたは実際のお金 $9 を — 静かに、繰り返し、離席するたびに — 失う。blockモードなら毎回それを止められる。

## 💡 キャッシュの実際の仕組み（そしてなぜほとんどのユーザーが40%以上を無駄にするのか）

Claude CodeはすべてのAPI呼び出しで会話履歴全体をモデルに送信する。「API呼び出し」とは「入力したメッセージ1件」を意味しない。1つのプロンプトが内部のツール呼び出し — Grep、Read、Edit、Write — をトリガーし、それぞれが個別のAPI呼び出しとなる。1つのプロンプトで10回以上のAPI呼び出しが発生することは珍しくない。

プロンプトキャッシュはこのコストを90%削減する。ただし、キャッシュには有効期限がある。

|                     | メインセッション                          | SubTask                                |
| ------------------- | ------------------------------------- | -------------------------------------- |
| キャッシュTTL           | 1時間 (ephemeral_1h)                 | 5分                                  |
| キャッシュ書き込み         | ＄10/MTok                              | ＄6.25/MTok                             |
| キャッシュリード          | ＄0.50/MTok                            | ＄0.50/MTok                             |
| キャッシュ期限切れ時  | コンテキスト全体が通常価格で再送信    | 影響小（コンテキストが小さいため）          |

キャッシュが有効でもコストは蓄積する。違いを示すための極端なシナリオを見てみよう。

| Status line | すべてのAPI呼び出し | 0 | ターミナルのステータスバーにレンダリング、会話コンテキストには入らない |

**セッションあたりの正味オーバーヘッド：約1,400トークン（最初の呼び出し後にキャッシュ）。**

Opus価格設定（$0.50/MTok キャッシュリード）で、これは **1回のAPI呼び出しあたり$0.0007** — 1セント未満の10分の1。100回呼び出しのセッションで：$0.07。

git-liteが有効の場合、プラグインはセッションあたり約1,920トークンを**節約する**（2,200を280に置き換え）。正味効果はマイナス — プラグインが削除するより消費するトークンは少ない。

**API従量課金ユーザーへ：** $3,000/月の支出でも、プラグインのオーバーヘッドは月$2未満。キャッシュ期限切れ防止による節約だけで（週1回の$9再送信ブロック）、1回のキャッチで1年分のオーバーヘッドをカバーできる。

## 💡 ヒント

### キャッシュを理解すればお金の行方がわかる

- **1プロンプト ≠ 1 API呼び出し。** ClaudeがGrep、Read、Editを呼び出すたびに、コンテキスト全体が再送信される。1つのプロンプトで10回以上のAPI呼び出しが発生することは珍しくない。不要なツール呼び出しを減らすための明確なプロンプトを書いてコストを削減する。
- **キャッシュタイマーは最後のAPI呼び出しからリセットされ、最後のプロンプトからではない。** 作業を続けている限りキャッシュは期限切れにならない。危険なのは離席すること。Token Guardianがいつ期限切れが起きたかを知らせ、`block` モードなら戻ってきたときにコンテキストをリセットするかそのまま続けるかを選べるよう、プロンプトを一度だけ止める。
- **コンテキストサイズ = コスト乗数。** 同じAPI呼び出しでも、20万トークンと80万トークンでは4倍のコスト差。ステータスライン [CTX] が35%（🟡）を超えたら、SubTaskにもっと委譲するシグナル。

### コストを削減する習慣

- **CLAUDE.mdをスリムに保つ。** すべてのAPI呼び出しでシステムプロンプトに読み込まれる。すべての行がコストになる。
- **重い作業をSubTaskに委譲する。** コード生成、マルチファイル編集、テスト実行はメインセッションに属さない。SubTaskはコンテキストが小さく、より安いキャッシュ層を持つ。
- **1時間以上離席する？** `/clear` → 戻ってきたら → `/s-continue`。コンテキストが $0 で復元される。
- **[5H] が70%以上（🟡）？** ペースを落とす。軽量なレビュータスクに切り替えるか、メインのAPI呼び出し数を減らすためにSubTask委譲を増やす。
- **サイドクエスチョンには `/btw` を使う。** 会話履歴に入らないため、コンテキストがスリムに保たれる。

### API従量課金：最も重要な習慣

上記すべてに加え、API固有の優先事項：

- **[CTX] をスピードメーターのように見る。** レート制限で止まることはないが、コンテキストが50万以上になると、すべてのAPI呼び出しが本来の2〜3倍のコストになる。`/clear` → `/s-continue` は無料でコスト乗数をベースラインにリセットする。
- **週次で `/usage-view` を実行する。** Max Planユーザーはレート制限に達したときに「痛い」と感じる瞬間がある。あなたにはそれがない — コストが静かに上昇する。ダッシュボードが早期警告システムになる。
- **日次の精神的な予算を設定する。** 上限がなければ、$200の日が気づかずに発生する。ステータスラインのRUNインジケーターがターンごとのコストを可視化する。1ターンが $1（🔴）を超えたら、コンテキストが大きすぎる。
