Status: LIVING. 다시 계산하지 말고 이 문서를 갱신한다. 마지막 실측 2026-09-04 17:00 KST.

## 1. 데이터 소스 (플러그인 캐시만 쓴다)

## 2. 구간 자르기

1. `ratelimit.csv` 전 파일의 `(ts, 5h%)`를 합쳐 정렬, 중복 제거.
2. 윈도우(run)로 나눈다. 2시간 넘게 비거나, 값이 run 최대치보다 8pt 넘게 떨어지고 **그 뒤 3샘플이 계속 낮으면** 새 run. 한 샘플만 낮은 것은 유휴 세션이 찍은 낡은 값이다(세션마다 자기 마지막 API 응답값을 찍으므로 같은 분에 70과 21이 같이 나온다).
3. run 안에서 상한 포락선(누적 최대)을 씌운다. 낡은 낮은 값은 실제 값을 낮출 수 없다.
4. 누적 상승이 처음 5pt 이상이 되는 샘플마다 자른다. 구간 Δ는 5~7.
5. **CC 밖 사용 걸러내기.** 구간 상승분 ÷ 그 구간 CC 정가 합이 1pt/$를 넘으면(가장 빠른 모델 Fable도 0.4pt/$) CC 사용으로는 그 상승이 나올 수 없다. 이런 구간은 claude.ai 웹·데스크톱·Chrome 확장 등 같은 5h 윈도우를 쓰는 다른 클라이언트의 몫이다. 9/4 11:11~13:23 구간이 그 예다 — CC 캐시읽기 2.8M(캐시=트랜스크립트 일치 확인)인데 20pt 올랐다. 419개 중 27개, 총 상승의 14%. 계수 적합에서 뺀다.
4. 구간 `[t0, t1]`에 `ts`가 들어가는 `timeline.csv` 행을 모델 그룹별로 5종 토큰 합산 (100만 단위).

한계: 5h%는 정수, 스테이터스라인 갱신 시점에만 기록, 리미터 집계와 타임스탬프 지연. 구간 하나는 못 믿는다. 합쳐야 의미가 있다. 5pt 구간 중앙 절대오차 약 1.2~1.4pt.

**프로모션 구간은 못 믿는다.** 경쟁으로 할인·추가 토큰·limit 초기화가 수시로 들어온다. limit 초기화는 지속되는 하락으로 잡혀 새 윈도우로 갈라지지만, 할인(같은 사용량에 덜 차는 날)은 데이터에 표시가 없어 걸러낼 수 없다. 그런 날이 섞이면 계수가 낮게 나온다. 계수를 인용할 때는 표본 날짜를 같이 적고, 이상하게 낮은 날은 프로모션 여부부터 의심한다.

**구간 단위로 맞는 비율 (CC 밖 구간 27개 제외, 392개).** 어떤 모형도 구간 전부를 맞추지는 못한다. 남는 것은 위 한계에서 오는 잡음이다.

| 모형 | 2pt 이내 | 3pt 이내 | 중앙 절대오차 |
|---|---|---|---|
| H1 정가 비례 (4 파라미터) | 67% | 78% | 1.24pt |
| H4 토큰 종류별 자유 계수 | 68% | 83% | 1.33pt |
| 입력·출력만 (캐시 무시) | 56% | 73% | 1.73pt |

모델별로는 Fable 5.1이 지배하는 구간(47개)에서 H1이 81% 2pt 이내, Opus 5 지배 구간(224개)에서 72%. Fable 계수가 구간 단위로 더 잘 맞는다.

## 2b. 계정이 둘이다 — 계정 A(주력)와 계정 B(보조)

데이터 어디에도 계정 이름은 없다. 대신 `ratelimit.csv`의 `7d_reset`이 계정마다 다르다: 계정 A는 15:00 KST 계열(8/14·8/21·8/28·9/4·9/11), 계정 B는 21:00 계열(8/27·9/3·9/10). 세션 도중 `/login`으로 바꾸기도 하므로(9/4 이 세션이 그랬다) 세션 단위가 아니라 **샘플 단위**로 가장 가까운 `7d_reset`의 계열을 붙이고, 5h 계열도 계정별로 따로 자른다. `7d_reset`은 샘플의 13%에만 있어 나머지는 같은 세션의 가장 가까운 태그를 물려받는다.

한계: 9/4 08:00~09:00처럼 두 계열이 똑같은 값을 찍는 구간이 있다 — 태그가 일부 잘못 붙는다는 뜻이다. 계정별 계수(§4)는 이 오차를 안고 있다.

**트랜스크립트로 계정 확정 (2026-09-27).** Claude Code는 세션 시작 때와 `/login`으로 계정을 바꾼 직후, 로그인 이메일을 `type: "attachment"`, `attachment.type: "session_context"` 줄로 적는다(2026-09-09 무렵부터. 그 전 트랜스크립트에는 없다). `analyze-usage.js`가 이 줄만 읽어 `summary.json`의 `accountChanges: [{ts, account}]`에 계정이 바뀔 때마다 한 건씩 남긴다. `account`는 소문자 이메일의 sha256 앞 12자리이며 솔트가 없다 — 아는 주소를 같은 방식으로 해시해 이름을 붙인다. 대화 속 인용이나 도구 결과는 이 줄 형식이 아니라 잡히지 않는다. 샘플의 계정 = 그 세션에서 샘플 시각 직전의 `accountChanges`. 이 줄이 없는 세션(`claude -p`·SDK, 9/9 이전)은 전체 세션 중 직전 로그인 계정을 쓰고, 그것도 없으면 위 `7d_reset` 계열로 판정한다. `statusline-logger.sh`에 열을 늘리는 방식은 행마다 데이터가 늘어 택하지 않았다. Codex 트랜스크립트에는 같은 기록이 없어 해당 없음. 회귀 테스트 `scripts/test-account-changes.js`.

## 2c. 고정 사실 (FACT — 재추정하지 않는다)

**캐시읽기 = 0.013 pt/M, 모델 무관 (Opus 5 · Fable 5.1 실측, 2026-09-04, 표본 기준).** 오차 ±0.002. 이후 모든 회귀·환산은 이 값을 상수로 놓고 나머지 종류(쓰기 1h·5m, 출력, 입력)만 추정한다. 근거·로우 데이터는 internal-docs `cc-token-saver/rate-limit-experiments/2026-09-04/`.

## 3. 회귀

- 모델 그룹 4개(Opus 5 · Fable 5.1 · Sonnet · other) × 변수 5개(a 입력, b 출력, c 캐시읽기, d 캐시쓰기 1h, e 캐시쓰기 5m) = 20개 비음수 최소제곱(NNLS). **구간을 모델 지배율로 거르지 않는다.** 서브에이전트(5m 캐시)는 항상 다른 모델과 같은 시간대에 돌아서 거르면 e가 사라진다.
- 가설 비교로 판정한다: H1 정가 비례(`cost` 열) / H2 캐시 할인 없이 입력 단가 / H3 토큰 수 / H4 자유 계수.
- 이미 해 본 것, 다시 하지 마라: **200K 초과 컨텍스트 요청**을 따로 두면 정가 1달러당 소진이 오히려 0.3배로 나온다 — 캐시읽기 비중이 큰 요청일수록 리미터가 정가보다 싸게 친다는 뜻이지 할증이 아니다. 공식 가격 페이지(2026-09-04 확인)도 "Claude 4.6 이후 모델은 1M 컨텍스트 전 구간 표준 단가"라고 적고 있어 장문 할증 자체가 없다. 참고로 Opus 5 요청의 78%가 200K를 넘는다.
- **입력·출력만으로는 안 된다.** 순수 입력·출력은 토큰의 0.2%라 캐시 몫까지 떠안은 계수가 나와 해석이 안 되고 적합도 가장 나쁘다.
- scipy 없는 환경이라 투영 경사법. 토큰 열은 반드시 100만으로 나눈다. 안 나누면 수렴 안 해 전부 0이 나온다. 부트스트랩은 반복 부족으로 점추정이 구간 밖에 놓인다. 신뢰구간으로 쓰지 않는다.

## 4. 확정 수치 (8/12 ~ 9/4 17:00, 5pt 구간 392개, Claude Code 트리만, CC 밖 구간 제외)

### Opus 5는 정가에 거의 비례한다

| 가설 | 파라미터 | 중앙 절대오차 |
|---|---|---|
| H1 정가 비례 | 4 | 1.24pt |
| H2 캐시 할인 없음 | 4 | 2.04pt (초기 436구간 기준) |
| H3 토큰 수 비례 | 4 | 2.04pt (초기 436구간 기준) |
| H4 자유 계수 | 20 | 1.33pt |

리미터는 캐시 읽기를 싸게 치는 것까지 가격표와 같은 방향이다. 자유 계수에서 c(캐시읽기)가 가격 함의값의 0.6배, d(1h 쓰기) 3.6배, e(5m 쓰기) 1.9배로 나오지만 읽기와 쓰기가 같은 요청에 붙어 나와 회귀가 둘 사이에서 포인트를 주고받은 것이다. 합치면 가격 비례와 같다. a·b는 토큰의 0.2%라 판정 불가.

### Opus 5 종류별 공식 (5pt 구간, 계정 A, 이벤트 날 제외 193개, Fable·기타는 정가 합으로 통제)

**이벤트 날 = 8/19 · 8/20 · 8/30 (사용자 확인).** 그날은 같은 토큰으로 2~4배 빨리 찼다. 제외한다.

```
5h 소진 pt = 0.030·캐시읽기(M) + 2.1·캐시쓰기1h(M) + 1.6·캐시쓰기5m(M) + 0.12·출력(M)   (입력 = 데이터 없음)
```

| 종류 | pt/M | 정가 함의 pt/M | 배수 | 표본 |
|---|---|---|---|---|
| 캐시읽기 | 0.030 | 0.041 | 0.7× | 9.1B |
| 캐시쓰기 1h | 2.08 | 0.82 | 2.6× | 98M |
| 캐시쓰기 5m | 1.56 | 0.51 | 3.1× | 23M |
| 출력 | 0.12 | 2.04 | 0.06× | 20M — 표본 작아 미확정 |
| 입력 | — | 0.41 | — | 0.1M, 추정 불가 |

**캐시읽기 계수 — 통제 실험으로 확정 (§2c 고정값) (2026-09-04, 계정 A).** 회귀로는 읽기·쓰기·출력이 같은 요청에 붙어 나와 갈리지 않았다(읽기를 0으로 강제해도 적합이 같았다). 그래서 직접 쟀다: 이 세션을 포크한 서브에이전트(컨텍스트 약 440K)가 `true` 명령을 1,000턴 호출. 요청 995건, 캐시읽기 441M, 캐시쓰기 0.51M, 출력 9.6K. 5h는 2→9%(+7pt, 그중 첫 3pt는 250회에 한꺼번에 반영), 7d는 5→6%. 그동안 이 계정에서 다른 사용 없음. 쓰기 몫(0.51M×2.1=1.1pt)을 빼면 **읽기 = 0.013 pt/M (±1pt 오차 감안 0.011~0.016)**. 즉 5h 100% = 캐시읽기 약 7.7B 토큰(정가 $3,850). 정가 비례 함의(0.041)의 1/3이고, 회귀 계수(0.030)의 절반 이하다. 리미터는 캐시읽기를 정가보다 훨씬 싸게 치지만 0은 아니다. 이 실측이 §3 회귀보다 우선한다 — 회귀의 읽기 계수는 쓰기·출력 몫을 일부 떠안은 값이다.

**Fable 5.1도 같은 실험으로 확정 (2026-09-04, 계정 A, 바로 이어서).** 같은 포크·같은 프로토콜, 모델만 Fable 5.1. 요청 1,001건, 캐시읽기 434.7M, 캐시쓰기 0.66M, 출력 10.9K. 5h 9→16%(1,000회 표본) / 17%(종료 직후), 7d 6→8%. 쓰기 몫(0.66M×2.1=1.4pt)을 빼면 **읽기 = 0.013 pt/M (±1pt: 0.011~0.015) — Opus 5(0.013)와 같다.** 250회에서 3pt가 한꺼번에 반영되는 계단까지 같았다. 회귀에서 나온 Fable 읽기 계수 0.16은 하루치 표본의 착시였다.

**결론이 바뀐다.** 구독 리미터는 캐시읽기를 모델과 무관하게 토큰당 같은 무게로 친다. Fable 캐시읽기 정가($0.25/M)가 Opus($0.50/M)의 절반이므로, **정가 달러당으로는 Fable이 Opus보다 2배 후하다.** "Fable이 5h를 4~5배 빨리 채운다"(§4 H1)는 회귀가 읽기 계수를 잘못 잡은 결과이며 철회한다. 남는 차이는 쓰기·출력 계수인데 Fable 쪽은 실측이 없다. Fable 쓰기·출력 실험이 없는 한 "같은 토큰 구성이면 두 모델의 5h 소진은 같다"가 현재 가장 근거 있는 진술이다. 사용자가 체감한 "Fable이 빨리 찬다"는 Fable 세션이 더 자주 캐시를 깨거나(쓰기), 서브에이전트(5m 쓰기)를 더 많이 돌린 결과일 가능성이 크다 — §4 Opus 쓰기 계수는 정가 함의의 2.4~3.7배다.

구간 적합: ±1pt 48%, ±2pt 78%, ±3pt 92%, 중앙 절대오차 1.03pt. 정가 비례(±2pt 75%)보다 낫다. 3pt 넘게 어긋난 구간은 193개 중 16개. 이벤트 날을 포함하면 ±2pt 69%, ±3pt 79%로 떨어진다. 두 계정을 합치면(303개) 읽기 0.038, 쓰기1h 2.2, 쓰기5m 1.8로 같은 자리다. 구간 하나(5~7pt)에서 캐시읽기가 중앙값 1.4pt, 쓰기가 0.6pt를 낸다. 리미터는 정가보다 캐시 쓰기를 두 배 무겁게, 캐시 읽기를 조금 가볍게 친다. 출력 계수가 정가의 1/10로 나오는 것은 출력이 쓰기와 같은 요청에 붙어 나와 쓰기 쪽에 흡수된 결과일 가능성이 크다 — 출력만 많은 실험 없이는 못 가른다.

**캐시쓰기 계수 = 2.2 pt/M (전수조사로 확인, 2026-09-04).** 8/12~9/4 Opus 5의 캐시쓰기 200K 이상 요청 218건에서, 요청 직전 표본 대비 뒤 3~30분 창의 최대 상승을 창 안의 다른 사용과 함께 회귀. 창 길이에 관계없이 2.1~2.5. 쓰기가 나중에 몰아서 정산된다는 가설은 이 자료로 기각. 정가 함의(0.82)의 2.7배. 5h 100% = 쓰기 1h 약 45M(정가 $450). 통제 실험의 250회 계단(3pt)은 쓰기로 설명되지 않으며 원인 미해결. 로우 데이터는 internal-docs.

**어긋남은 이벤트 날에 몰려 있었다.** 이벤트 날을 포함한 242개에서는 3pt 넘게 어긋난 50개 중 44개가 실제가 예측보다 큰 쪽이었고, 8/30이 21개 중 17개(정가 $1당 0.42pt, 평소의 4배, 7d가 하루에 16→61%), 8/19~20이 28개 중 15개(0.18~0.24pt/$, 7d 86→98%)였다. 주간 잔량과 같이 움직이는 것처럼 보였지만(7d 0~40% 0.128pt/$ → 80%+ 0.217) 이벤트 날이 주 후반이었던 탓일 수 있다. 새 날짜가 이상하게 빠르면 먼저 이벤트 여부를 확인하고 제외한다.

**한 요청이 %를 튀게 하지는 않는다 (확인함).** 캐시가 깨져 한 요청에 500~760K를 쓴 경우(계정 A 상위 25건) 직전·직후 샘플 차이는 0~3pt, 중앙값 1pt로 공식(1.1~1.5pt)과 같다. 출력 10K 이상 요청 50건도 0~1pt다. 반대로 한 샘플 사이에 15~49pt 뛴 지점은 그 사이 요청이 0~2건이라 토큰이 아니라 낡은 샘플·계정 전환·CC 밖 사용이다. 큰 요청을 찾아 원인으로 삼지 마라.

**Fable 5.1에 읽기=0 모형을 얹어도 배율은 그대로다.** Fable 구간 46개(9/4, 정가 $543, 읽기 572M·쓰기 20M·출력 1.5M). 읽기=0 모형은 Fable에서는 오히려 덜 맞고(±3pt 83% 대 5종 91%), 그때 쓰기 7.8pt/M·출력 51pt/M이 필요하다 — Opus의 읽기=0 모형(쓰기 1.9·출력 13.9)의 4배. 읽기를 살리면 Fable 읽기 0.16pt/M(Opus 0.030의 5배), 쓰기 8.8(Opus 2.1의 4배). 어느 모형이든 같은 종류의 토큰 하나당 Fable이 Opus의 4~5배다. Fable/Opus 배율은 읽기 가중치를 어떻게 두느냐에 안 흔들린다.

## 5. `--all` 총액 누락 버그 (2026-09-04 발견·수정)

**증상.** `/usage-view --all` 총액이 실제의 절반이었다. 26일 기준 $7,555 → 수정 후 $14,764.

**원인.** `statusline-logger.sh`는 세션이 `cd`한 현재 cwd의 해시로 `{proj}/{sid}/ratelimit.csv`를 만든다. 한 세션이 하위 폴더·worktree를 오가면 같은 `sid` 폴더가 프로젝트 여러 개 아래에 생긴다(한 세션이 10개). `build-report.js`의 디렉터리 스캔은 마지막 프로젝트가 이겼고, 그 폴더에는 `timeline.csv`가 없어 그 세션 비용이 0이 됐다. 메인 세션 97개, $7,192. 큰 세션일수록 `cd`가 많아 더 잘 빠졌다. `--project` 단독 실행은 영향 없음.

**수정.** `build-report.js`가 `raw.sessions[].filePath`에서 `extractProjectName()`으로 프로젝트를 정한다. `analyze-usage.js`가 캐시 폴더를 정할 때 쓰는 규칙과 같다. 회귀 테스트 `scripts/test-session-project-map.js` (같은 sid를 프로젝트 3개 아래에 두고 총액 확인. 수정을 되돌리면 0으로 떨어지는 것을 확인함).

**검증 (수정 후).** 트랜스크립트 JSONL을 직접 합산한 독립 기준값과 리포트가 토큰 5종 전부 0.04~0.13% 안에서 일치. 합산 규칙은 **요청당 마지막 usage 줄** — 스트리밍 중간 줄은 부분 출력값(8→282)이라 첫 줄을 쓰면 출력이 34% 빠진다. 서브에이전트 파일의 부모 복사 행은 requestId로 걸러야 하며 26일 기준 $262뿐이다. `--force` 재분석은 총액을 $11 바꿨다(가격표 캐시는 원인이 아님).

**합산 규칙 3가지 (2026-09-27 확정)** — 같은 requestId가 두 번 보일 때 경우마다 처리가 다르다.

## 6. 다시 돌리는 법

`scripts/`에 넣지 않았다. 손 스크립트는 세션 스크래치에 있었고 버렸다. 이 문서 §2·§3대로 다시 쓰면 30분이다. 트랜스크립트를 직접 훑을 일이 있으면 `subagents/workflows/wf_*/agent-*.jsonl`(Workflow 에이전트, 줄 타입 `message`)까지 재귀로 잡아야 한다 — 분석기는 이미 잡는다(캐시 `subagents/{agentId}/`). 제품 기능으로 굳히려면 `report-limit.js`에 §2 구간 자르기와 §3 H1 적합을 넣고 모델별 "정가 $1당 pt"를 대시보드 카드로 낸다.
