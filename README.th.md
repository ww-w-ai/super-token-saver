# super-token-saver

**ปลั๊กอิน Claude Code เดียวที่อ่านซอร์สโค้ดของ CC จริงๆ เพื่อค้นหาว่าโทเค็นของคุณไปอยู่ที่ไหน — และแก้ไขมันโดยอัตโนมัติ ใช้จ่ายน้อยลง ทำงานได้นานขึ้น**

> ผลลัพธ์ที่วัดได้: **ลดต้นทุน 45%** บนภาระงานจริง $326/วัน → $180/วัน มอบหมาย SubTask อัตโนมัติ, กู้คืนคอนเทกซ์โดยไม่มีค่าใช้จ่าย, แดชบอร์ดวิเคราะห์ครบชุด และตัวเฝ้าระวังแคชหมดอายุ — ในการติดตั้งเดียว ไม่ต้องตั้งค่า

ทำงานกับ **Max Plan ($200/เดือน)** และ **API แบบจ่ายตามการใช้งาน** ปลั๊กอินเดียวกัน ฟีเจอร์เดียวกัน แข็งแกร่งกว่าสำหรับทุกผู้ใช้ — โดยเฉพาะเมื่อทุกโทเค็นคือเงินจริง

## 🧠 ฟีเจอร์ 1: Smart Session Architecture

**ติดตั้งแล้วรูปแบบการทำงานที่เพิ่มประสิทธิภาพต้นทุนจะเริ่มทำงานโดยอัตโนมัติ**

ผู้ใช้ส่วนใหญ่ทำทุกอย่างใน Main session การอ่านไฟล์ การสร้างโค้ด การรันทดสอบ ทุก output สะสมในคอนเทกซ์และถูกส่งซ้ำกับทุกข้อความ Session บวม ต้นทุนพอกพูน

Session Architect ฉีดกลยุทธ์การมอบหมายโดยอัตโนมัติเมื่อเริ่ม session

|                  | Main Session                      | SubTask                               |
| ---------------- | --------------------------------- | ------------------------------------- |
| บทบาท            | การออกแบบ การตัดสินใจ การตรวจสอบ  | การนำไปใช้ การสร้างโค้ด หลายไฟล์     |
| ระดับแคช         | 1 ชั่วโมง (ephemeral_1h)           | 5 นาที                                |
| ต้นทุนการเขียนแคช | ＄10/MTok                          | ＄6.25/MTok                            |
| ขนาดคอนเทกซ์     | ~94K เฉลี่ย                        | ~33K เฉลี่ย                            |

SubTask มีการเขียนแคช **ถูกกว่า 37.5%** กว่า Main คอนเทกซ์ก็เล็กกว่ามากด้วย การมอบหมายงานหนักให้ SubTask ลดต้นทุนได้อย่างมาก

**ผลลัพธ์:** คอนเทกซ์อยู่ต่ำกว่า 250K แทนที่จะโตถึง 600K+ output งานเท่ากัน ต้นทุนโทเค็นครึ่งเดียว อัตโนมัติทั้งหมด

## 🪶 Concise Mode

**เนื้อหาเดิม Padding น้อยลง เปิดใช้งานโดยค่าเริ่มต้น**

SessionStart hook ยังฉีดกฎรูปแบบการตอบกลับที่ทำงานใน **ทุก session และทุกโมเดล** — ไม่มี flags ไม่มีการตั้งค่า สามสิ่งที่เปลี่ยนแปลง:

- **ไม่มีคำนำ** — ไม่มี "ให้ฉันตรวจสอบ...", "ฉันจะ...", การพูดซ้ำคำถามของคุณ หรือสรุปสิ่งที่ diff แสดงอยู่แล้ว
- **รูปแบบที่เหมาะสมสำหรับเนื้อหา** — bullet สำหรับรายการ ร้อยแก้วสำหรับการให้เหตุผล (การแลกเปลี่ยน เหตุผล การอธิบาย) ไม่บังคับอะไรทั้งนั้น
- **การแสดงออกที่กระชับขึ้น** — ประเด็นเดิม คำน้อยลง ร้อยแก้วที่ชัดเจนกว่าคือร้อยแก้วที่สั้นกว่า

ขีดจำกัดที่เข้มงวด: ไม่ตัดเนื้อหา ไม่ข้ามการตรวจสอบ หรือบีบอัดความละเอียดอ่อนลงในประโยคเดียว เนื้อหาคงเต็ม ลดแค่ wrapper

## 🔄 ฟีเจอร์ 2: /s-continue — การกู้คืนคอนเทกซ์

**แทนที่ `/compact` ศูนย์การเรียก LLM ศูนย์ต้นทุนโทเค็น ศูนย์ข้อมูลสูญหาย**

`/compact` ส่งคอนเทกซ์ทั้งหมดของคุณ (~1M โทเค็น) ไปยัง LLM เพื่อบีบอัดเป็นสรุป 3.3% หากแคชหมดอายุ นั่นเพียงอย่างเดียวก็กระตุ้นให้มีการ re-cache แบบเต็ม การสูญเสียข้อมูลเป็นสิ่งที่หลีกเลี่ยงไม่ได้

`/s-continue` ใช้แนวทางที่แตกต่างไปโดยสิ้นเชิง มันประมวลผล transcript ของ session ก่อนหน้าล่วงหน้าและโหลดโดยตรง ไม่มีการเรียก LLM ไม่มีค่าใช้จ่าย การสนทนาเดิมถูกกู้คืนตามสภาพ

|                         | /compact                                      | /s-continue                                   |
| ----------------------- | --------------------------------------------- | ------------------------------------------- |
| วิธีการทำงาน            | ส่งคอนเทกซ์เต็มไปยัง LLM เพื่อสรุป           | ประมวลผล transcript ล่วงหน้า อ่านโดยตรง    |
| การเรียก LLM            | จำเป็น (โดยทั่วไป 100K+ โทเค็น)               | 0                                           |
| ต้นทุนโทเค็น             | สูง                                           | 0                                           |
| การสูญเสียข้อมูล        | ใช่ (สรุป 3.3%)                               | ไม่มี (เก็บต้นฉบับไว้)                      |
| ความเร็วในการประมวลผล   | หลายสิบวินาที                                  | < 1 วินาที (แม้ไฟล์ขนาด 60MB+)             |
| เมื่อแคชหมดอายุ         | ต้นทุน re-cache เต็มรูปแบบเพิ่มเติม            | ไม่มีผลกระทบ                                |
| การกู้คืนหลาย session   | ไม่สามารถทำได้                                  | รองรับ                                      |

การใช้งาน: `/clear` แล้ว `/s-continue` คุณจะเห็นรายการ session ก่อนหน้า เลือกรายการที่ต้องการกู้คืน สำหรับการกู้คืนด่วน: `/s-continue last`

**ผลลัพธ์:** กลับมาทำงานก่อนหน้าโดยไม่มีค่าใช้จ่าย ไม่มีข้อมูลสูญหาย ประมวลผล transcript ขนาด 60MB+ ในเวลาน้อยกว่า 1 วินาที

### 🤝 คู่หูของมัน: `/s-compact` — ส่งต่อเลเยอร์ที่ซ่อนอยู่

`/s-continue` กู้คืน **transcript** — สิ่งที่คุณและ Claude พูดคุยกัน แต่ความรู้ที่มีประโยชน์ที่สุดของ session การทำงานมักอยู่ **นอก** บทสนทนานั้น: สิ่งที่ **subagent** ค้นพบ (transcript ของมันเป็นไฟล์แยกที่การกู้คืนไม่เคยโหลด), **ตัวเลขสำคัญในผลลัพธ์ของเครื่องมือ** (จำนวนการทดสอบ, ค่า benchmark), **บทเรียนจากกระบวนการทำงาน** ("reproduce แบบ headless ไม่ได้ → ที่จริงเป็นปัญหาที่ build ไม่ใช่โค้ด")

รัน `/s-compact` ตอนจบ session แล้วมันจะกลั่นเลเยอร์ที่ซ่อนอยู่นี้ให้เป็นบันทึกส่งต่อ บันทึกไว้ที่ `~/.claude/super-token-saver-data/<project>/handoff.md` ใน session ถัดไป `/s-continue` จะ **โหลดอัตโนมัติ** ทับบน transcript ที่กู้คืนมา — ไม่ต้องวางเอง

|                     | `/s-continue` เดี่ยว            | `/s-compact` + `/s-continue` (ชุดคู่)          |
| กู้คืนอะไร            | transcript (สิ่งที่พูดคุยกัน)  | transcript บวกเลเยอร์ที่ซ่อนอยู่             |
| สิ่งที่ subagent พบ   | สูญหาย (ไฟล์แยก)           | กลั่นเก็บไว้ในบันทึกส่งต่อ                       |
| ตัวเลขจากผลลัพธ์เครื่องมือ | เฉพาะที่ถูกยกมาพูดในแชท    | ดึงออกมาอย่างตั้งใจ                            |
| บทเรียนจากกระบวนการ     | —                               | บันทึกไว้เพื่อไม่ต้องเจอทางตันซ้ำ              |

**ขั้นตอนการทำงาน:** จบ session ด้วย `/s-compact` → เริ่ม session ถัดไปด้วย `/s-continue`

### 🔀 สองเครื่องมือ ประวัติเดียวกัน — session ของ Codex ก็กู้คืนได้ที่นี่เช่นกัน

Codex เขียน session ของมันไว้ที่ `~/.codex/sessions/` ส่วน Claude Code เขียนไว้ที่ `~/.claude/projects/` ไม่มีเครื่องมือไหนอ่านไฟล์ของอีกฝั่งเลย เพราะฉะนั้น sprint ที่งบหมดกลางคันใน Codex เมื่อก่อนจะเข้าไม่ถึงจาก Claude Code เลย และก็เป็นแบบเดียวกันในทางกลับกัน

ตอนนี้ `/s-continue` แสดงรายการและกู้คืนได้ทั้งสองแบบ rollout ของ Codex ไม่ได้ถูกส่งให้ parser ตัวที่สองมาแปลง แต่จะถูกเขียนใหม่ให้อยู่ในรูปแบบเดียวกับที่ Claude Code เขียน **หนึ่งบรรทัดผลลัพธ์ต่อหนึ่งบรรทัดต้นฉบับ** ทำให้ pipeline เดียวกันรองรับทั้งสองเครื่องมือ และ marker `L{n}` แต่ละตัวยังคงชี้ไปยังบรรทัดที่ถูกต้องในไฟล์ Codex ต้นฉบับ วัดผลได้ว่า rollout ขนาด 12 MB จำนวน 1,540 บรรทัด ประมวลผลล่วงหน้าเสร็จภายใน **0.13 s**

| ---------------------- | ------------------- | ------------- |

```
/s-continue codex : rust migration   turn ที่ตรงกับหัวข้อนั้น กู้คืนมาแบบเต็ม
```

รายละเอียดสองอย่างที่ทำให้รายการที่ถูกต้องต่างจากรายการที่ดูเหมือนถูกแต่ผิด: `session_id` ของ Codex แท้จริงแล้วคือ id ของ **thread** ซึ่ง subagent ที่ถูก spawn ขึ้นมาจะสืบทอดค่านี้ไปด้วย ดังนั้น session จึงถูก key ด้วย `payload.id` แทน และ rollout ของ subagent จะถูกกรองออกด้วยวิธีเดียวกับที่ transcript ของ subtask ใน Claude Code ถูกกรองออกอยู่แล้ว ส่วน `<codex_internal_context source="goal">` ถูกแทรกเข้ามาโดยระบบเอง จึงยังคงอยู่ในคอนเทกซ์ที่กู้คืนมา แต่จะไม่ถูกนับเป็น turn ที่คุณพิมพ์เอง

ปลั๊กอินนี้ติดตั้งลงใน Codex ได้ด้วยเช่นกัน — ดูที่ **[README-CODEX.md](./README-CODEX.md)** ([한국어](./README-CODEX.ko.md) · [日本語](./README-CODEX.ja.md) · [简体中文](./README-CODEX.zh-Hans.md)) ส่วน `usage-view`, `report-limit` และ `setup-statusline` ยังคงใช้ได้เฉพาะ Claude Code เท่านั้นในตอนนี้

## 📊 ฟีเจอร์ 3: Status Line แบบสด

**การตรวจสอบโทเค็น/ต้นทุนแบบเรียลไทม์ Overhead ต่ำกว่า 50ms**

รัน `/setup-statusline install` ครั้งเดียวและ status bar ถาวรจะปรากฏที่ด้านล่างของ Claude Code

**การทำงานปกติ** — ตรวจสอบทุก metric ด้วยสายตาเดียว ไม่ต้องสลับคอนเทกซ์:

![Status line ในสถานะปกติ](docs/images/statusline-normal.png)

**โดน rate limit** — 5H เป็นสีแดงที่ 102%, นับถอยหลังแสดงว่าคุณจะกลับมาได้เมื่อไร และ action `/report-limit` แบบแตะครั้งเดียวจะปรากฏโดยอัตโนมัติ:

![Status line เมื่อถูก rate limited](docs/images/statusline-rate-limited.png)

| ตัวบ่งชี้        | สิ่งที่แสดง                               | 🟢 ปกติ   | 🟡 เตือน  | 🔴 วิกฤต  |
| ---------------- | ----------------------------------------- | --------- | --------- | --------- |
| RUN (delta)      | ต้นทุนของ API call ล่าสุด                  | < ＄0.30   | >= ＄0.30  | >= ＄1.00  |
| RUN (สะสม)       | ต้นทุนสะสมสำหรับโฟลเดอร์นี้               | —         | —         | —         |
| 5H               | การใช้งานหน้าต่าง 5 ชั่วโมง + นับถอยหลังรีเซ็ต | < 70% | >= 70%    | >= 90%    |
| CTX              | การใช้งานหน้าต่างคอนเทกซ์                  | < 35%     | >= 35%    | >= 70%    |

เมื่อตัวบ่งชี้ใดๆ ถึงระดับเตือนหรือวิกฤต คำแนะนำ `→ /usage-view current` จะปรากฏโดยอัตโนมัติ

เพื่อลบ: `/setup-statusline uninstall` (การตั้งค่าก่อนหน้าถูกกู้คืนอัตโนมัติ)

**ผลลัพธ์:** ปัญหาต้นทุนทุกอย่างมองเห็นได้แบบเรียลไทม์ Overhead ต่ำกว่า 50ms — ไม่มีความล่าช้าที่รู้สึกได้

> **ใช้ API แบบจ่ายตามการใช้งาน?** ตัวบ่งชี้ 5H และ W ซ่อนตัวเองโดยอัตโนมัติ — คุณไม่มีหน้าต่าง rate limit สิ่งที่เหลือคือสิ่งที่สำคัญ: RUN (ต้นทุนเรียลไทม์ต่อเทิร์น) และ CTX (ขนาดคอนเทกซ์) สองตัวควบคุมบิลของคุณ มองเห็นได้เสมอ

## 📈 แดชบอร์ดการใช้งาน (/usage-view)

**ตอบคำถามได้ในที่สุดว่า: "เงินทั้งหมดนั้นไปไหน?"**

ผู้ใช้ Max Plan โดน rate limit แล้วสงสัยว่าทำไม ผู้ใช้ API เปิดใบแจ้งหนี้ Anthropic แล้วสงสัยว่าอย่างไร ไม่ว่าจะแบบไหน คำถามเดิม: session ไหนเผาโทเค็นมากที่สุด? ต้นทุนพุ่งขึ้นเมื่อไร? มีรูปแบบอะไรในการใช้งานของคุณ? จนถึงตอนนี้ — ทั้งหมดมองไม่เห็น

`/usage-view` แสดงทุกอย่าง แดชบอร์ด HTML แบบอินเทอร์แอคทีฟเปิดในเบราว์เซอร์ของคุณ ให้คุณวิเคราะห์รูปแบบการใช้งานและติดตามสาเหตุหลักของการพุ่งต้นทุน ไม่มีการพึ่งพาภายนอก ทำงานแบบอิสระ แชร์ได้เป็นไฟล์

**$4,196 ใน 31 วัน ไปอยู่ที่ไหน?** มองครั้งเดียว — ต้นทุนรวม การแบ่งย่อยโทเค็นตามประเภท อัตราประสิทธิภาพแคช และจำนวน session แผนภูมิโดนัทแสดงทันทีว่า 65% ของการใช้จ่ายของคุณเป็นการอ่านแคช (ซึ่งปกติและดี):

![ภาพรวมแดชบอร์ดการใช้งาน](docs/images/usage-view-overview.png)

**ก่อนเทียบกับหลัง — วัดได้ ไม่ใช่เดา** เส้นประ "Plugin installed" สีส้มแบ่งไทม์ไลน์ต้นทุนของคุณออกเป็นสองส่วน แท่งรายวันถูกเรียงซ้อนตามประเภทโทเค็น (Input/Output/Cache Write/Cache Read) เพื่อให้คุณเห็นว่าคอมโพเนนต์ไหนเปลี่ยนแปลงหลังการติดตั้ง เส้นเฉลี่ยแสดงแนวโน้ม:

![แนวโน้มต้นทุนรายวัน](docs/images/usage-view-daily-trend.png)

**คุณเผาเงินมากที่สุดเมื่อไร?** ต้นทุนรายชั่วโมงตามช่วงเวลาของวันและการแบ่งย่อยตามวันในสัปดาห์ สลับระหว่างค่าเฉลี่ยวันที่ใช้งาน ค่าเฉลี่ยทุกวัน หรือสูงสุด ไอคอนไฟทำเครื่องหมายชั่วโมงที่แพงที่สุดของคุณ — รูปแบบที่มองเห็นได้ (มาราธอนดึก สไปค์วันพุธ) เด่นชัดทันที:

![รูปแบบต้นทุนรายชั่วโมงและตามวันในสัปดาห์](docs/images/usage-view-hourly-pattern.png)

**คุณมีประสิทธิภาพมากขึ้นไหม?** อัตราส่วน Total/Output วัดว่ามีโทเค็นถูกใช้เท่าไรต่อโทเค็น output หนึ่งที่ผลิตออกมา ยิ่งต่ำยิ่งดี เครื่องหมาย "Plugin installed" ให้คุณเปรียบเทียบก่อนและหลัง สไปค์ = cache miss หรือการรีสตาร์ท session:

วางเมาส์บนจุดใดก็ได้เพื่อดูข้อความ prompt จริง จำนวนโทเค็น และการแบ่งย่อยต้นทุนแบบสมบูรณ์ (Input/Output/Cache Write/Cache Read):

```
/usage-view private          # ลบข้อความ prompt (ปลอดภัยสำหรับแชร์)
```

## ✂️ ฟีเจอร์ 4: /setup-git-lite — ตัดคำสั่ง Git ในตัวของ CC

**เราอ่านซอร์สโค้ดของ Claude Code แล้วพบ 2,200 โทเค็นซ่อนเร้นที่ถูกฉีดเข้ามาทุก session ซึ่งคุณจ่ายอยู่เงียบๆ**

### การค้นพบ

ในวันที่ 2026-04-12 [GitHub issue](https://github.com/anthropics/claude-code/issues/47107) เปิดเผยว่าการตั้งค่า `includeGitInstructions` ในตัวของ Claude Code เผาโทเค็นอย่างเงียบๆ ทุก session การทำซ้ำอิสระผ่าน [gist นี้ (spilist)](https://gist.github.com/spilist/b0db92a859192f5ec6199d3f35a81b98) ยืนยันตัวเลข: **+6,031 โทเค็นในการเขียนแคช** ต่อ session หลังจาก git commit ทุกครั้ง, **+1,690 โทเค็นในการอ่านแคช** ทุก API call

### การวิเคราะห์ซอร์ส CC — โทเค็นไปอยู่ที่ไหน

เราตามรอยโทเค็นไปถึงจุดฉีดสองจุดที่เป็นอิสระในซอร์สโค้ด Claude Code (v2.1.88):

**1. Snapshot `gitStatus` (~500 tok) — system prompt**
- `context.ts:36-111` `getGitStatus()` รวบรวม branch + main branch + user.name + status เต็มรูปแบบ (ถึง 2000 ตัวอักษร) + **5 commit ล่าสุด**
- รวมเข้าและต่อท้ายใน system prompt ผ่าน `appendSystemContext` (`utils/api.ts:437`)
- ทุก commit ใหม่ ทุกไฟล์ที่แก้ไขใหม่ ทุกการสลับ branch เปลี่ยนข้อความ → การทำให้แคช prefix ไม่ถูกต้อง

**2. คำสั่งเวิร์กโฟลว์ Commit/PR (~1,700 tok) — คำอธิบายเครื่องมือ Bash**
- `tools/BashTool/prompt.ts:53` เพิ่ม 60+ บรรทัดของโปรโตคอลความปลอดภัย ขั้นตอน commit ทีละขั้น ตัวอย่าง HEREDOC และเทมเพลตการสร้าง PR ไปยังคำอธิบายเครื่องมือ `Bash`
- Cache ร่วมกับ system prompt แต่ส่งเป็นพารามิเตอร์ `tools[]`

### ทำไมถึงแพง

โครงสร้างแคช (`utils/api.ts:321` `splitSysPromptPrefix`) มีสามเส้นทางขึ้นอยู่กับว่าคุณมีเครื่องมือ MCP ที่ใช้งานอยู่หรือไม่:

- **เส้นทาง A** (MCP active — ผู้ใช้ส่วนใหญ่): `gitStatus` อยู่ในบล็อก `cacheScope: 'org'` การเปลี่ยนแปลงใดๆ → บล็อกทั้งหมดถูก re-cache เมื่อเริ่ม session ถัดไป → `cache_create` miss 6K tok
- **เส้นทาง B** (ไม่มี MCP): `gitStatus` ไปยังบล็อกไดนามิก `cacheScope: null` ซึ่งหมายความว่าส่งซ้ำเป็น `input_tokens` ใหม่ทุก API call — ไม่มี cache miss แต่ก็ไม่มีการประหยัดแคช
- **เส้นทาง C** (ผู้ให้บริการ 3P / betas ทดลองถูกปิดใช้): เหมือนเส้นทาง A

ใน session เชิงโต้ตอบทั่วไป คำสั่ง commit/PR (1.7K tok) สะสม **ทุก API call** ผ่าน `cache_read` ใน session 100-call ที่ราคา Opus 4.7 นั่นคือประมาณ **$0.08 ต่อ session** เพียงแค่สำหรับคำสั่งที่การฝึกของ Claude ครอบคลุมอยู่แล้วส่วนใหญ่

### super-token-saver จัดการอย่างไร

`/setup-git-lite` ปิดใช้งานเส้นทางเดิมและฉีด **การแทนที่ 280-token ที่คัดสรรมาแล้ว** ผ่าน SessionStart hook เราเก็บไว้เฉพาะสิ่งที่แทนที่พฤติกรรมเริ่มต้นของ Claude (กฎความปลอดภัย) และทิ้งทุกอย่างที่ Claude รู้แล้วจากการฝึก (เวิร์กโฟลว์ทีละขั้น เทมเพลต PR รูปแบบการใช้งาน gh)

**เก็บไว้ — 11 กฎการแทนที่ที่สำคัญ** (กฎที่เปลี่ยนความเป็นมิตรเริ่มต้นของ Claude ให้กลายเป็นความระมัดระวัง):
- ไม่ commit/push/amend/PR/tag/merge โดยไม่มีคำขอชัดเจนจากผู้ใช้
- ไม่ข้าม hooks, force-push ไป main/master, รัน destructive ops, แก้ไข git config
- ไม่ commit ไฟล์ที่ตรงกับ `.env`, `credentials`, `*.pem`, `secret.*`
- หลีกเลี่ยง `git add -A` / `git add .`
- HEREDOC สำหรับข้อความ commit หลายบรรทัด + trailer `Co-Authored-By: Claude`
- ไม่ใช้ interactive flags (-i), ไม่ commit ว่าง
- ถ้า pre-commit hook ล้มเหลว → สร้าง commit ใหม่ (ไม่ใช่ `--amend`)

**ทิ้งไป** — เวิร์กโฟลว์ commit ทีละขั้น (3 ขั้น), เวิร์กโฟลว์ PR ทีละขั้น (3 ขั้น), เทมเพลตชื่อ/เนื้อหา PR, การอ้างอิงคำสั่ง `gh`, คำเตือน flag `-uall`, คำเตือน `--no-edit` กับ rebase, ข้อจำกัด `NEVER use TodoWrite or Agent tools during commit` สิ่งเหล่านี้คือความ verbose ของเวิร์กโฟลว์ที่ Claude ประกอบได้ถูกต้องจากการฝึกเพียงอย่างเดียว

**เพิ่มเข้ามา** — บรรทัดสถานะ git ที่กะทัดรัด: branch + HEAD short-sha + หัวเรื่อง + สถานะปัจจุบัน (ถึง 20 ไฟล์ที่แก้ไข ไม่งั้นนับ) ไม่มีรายการ commit ล่าสุด (Claude สามารถรัน `git log` ตามต้องการ)

### การใช้งาน


### ความหมายของการติดตั้ง

`install` แก้ไข **สองที่** เพื่อความแข็งแกร่ง:

1. `~/.claude/settings.json` — เพิ่ม `"includeGitInstructions": false`
2. Shell profile (`~/.zshrc`, `~/.bashrc`, ฯลฯ) — ต่อท้ายบล็อก marker ที่ export `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`

อย่างใดอย่างหนึ่งเพียงพอที่จะปิดใช้งาน CC native เราตั้งทั้งสองเพื่อไม่ให้การแทนที่สภาพแวดล้อมเปิดใช้งานพฤติกรรมดั้งเดิมโดยไม่ตั้งใจ การเปลี่ยนแปลง shell มีผลเฉพาะใน shell ใหม่เท่านั้น

### ความหมายของการ revert — เชิงรุก

`revert` **ลบ exports `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS` ทั้งหมดออกจาก shell profile ของคุณ** รวมถึงที่คุณอาจเพิ่มด้วยตนเองก่อนติดตั้ง skill นี้ นี่เป็นเจตนา — คุณรัน `revert` ดังนั้นเราจึงกู้คืนค่าเริ่มต้นที่สะอาด เราสร้างสำเนาสำรองที่มีการประทับเวลาของ shell profile เสมอก่อน

หากคุณต้องการตัวแปรสภาพแวดล้อมด้วยเหตุผลที่ไม่เกี่ยวข้อง จดบันทึกไว้ก่อนรัน `revert` แล้วเพิ่มกลับหลังจากนั้น

### ก่อนถอนการติดตั้ง super-token-saver

**รัน `/setup-git-lite revert` ก่อน** หรือคุณจะเหลือ `includeGitInstructions: false` ใน settings.json แต่ไม่มี hook แทนที่ (Claude จะไม่ได้รับคำแนะนำ git เลย) Claude Code ปัจจุบันไม่มี lifecycle hook สำหรับการถอนการติดตั้งปลั๊กอิน ดังนั้นเราไม่สามารถทำให้เป็นอัตโนมัติได้

### การแลกเปลี่ยน

สิ่งที่คุณสูญเสีย (และทำไมปกติก็ไม่เป็นไร):
- Claude ไม่ได้รับ `git status` / `git log -n 5` ที่คำนวณล่วงหน้าเมื่อเริ่ม session อีกต่อไป ถ้าคุณถามว่า "มีอะไรเปลี่ยนแปลง?" ใน session ใหม่ Claude จะรันคำสั่งเหล่านั้นเอง (การเรียกเครื่องมือพิเศษหนึ่งรายการ ~300 tok)
- Claude ไม่เห็นขั้นตอน commit 3-step ของ CC อีกต่อไป ในการทดสอบของเราบน commit flow หลายร้อยรายการ ความรู้ระดับการฝึกจัดการกรณีวิกฤต (รูปแบบ HEREDOC, ไม่ใช้ `--amend`, ไม่ force-push) เพราะเราเก็บไว้เป็นกฎชัดเจน
- เทมเพลตเนื้อหา PR (`## Summary` + `## Test plan`) ไม่ถูกฉีดเข้ามา ถ้าคุณสนใจรูปแบบนั้นพอดี ให้วางไว้ใน CLAUDE.md ของโปรเจกต์ของคุณ

### แบนเนอร์คำแนะนำ

เมื่อคำสั่ง git native ของ CC ยังคงใช้งานอยู่บนเครื่องของคุณ super-token-saver แสดงคำแนะนำหนึ่งย่อหน้าเมื่อเริ่ม session **~20% ของเวลา** (บวกกับใน output ของ `/usage-view` และ `/report-limit`) ปิดถาวรด้วย `/setup-git-lite dismiss-banner`

Token Guardian จำเวลาที่ได้รับการตอบกลับล่าสุดไว้ หากผ่านไปมากกว่า 3,590 วินาที (TTL ลบบัฟเฟอร์ 10 วินาที) มันสามารถเข้ามาทำงานได้ **แต่ตามค่าเริ่มต้นมันถูกปิดไว้ เพราะ Remote Control** ข้อความบล็อกจาก hook จะถูกแสดงในเครื่องเป็น system message ที่ remote client ไม่มีวันได้รับ ทำให้ผู้ใช้งานระยะไกลเห็น prompt หายไปเฉยๆ โดยไม่มีคำอธิบายใดๆ แทนที่จะปล่อยตัวป้องกันที่ทำงานต่างกันไปตามที่ที่คุณนั่งอยู่ เราจึงปิดมันไว้ก่อน เมื่อ Remote Control เริ่มส่งต่อข้อความจาก hook ได้ ค่าเริ่มต้นจะกลับมาเปิดอีกครั้ง จนกว่าจะถึงตอนนั้น คุณเปิดมันเองได้ด้วยหนึ่งในสองโหมด

```
export CC_TOKEN_SAVER_CACHE_GUARD=warn    # Claude จะพูดถึงการหมดอายุในบรรทัดแรกของคำตอบ
export CC_TOKEN_SAVER_CACHE_GUARD=block   # prompt จะถูกปฏิเสธหนึ่งครั้งพร้อมข้อความด้านล่าง
```

ในโหมด `warn` prompt ผ่านไปได้ตามปกติ และ Claude จะเปิดคำตอบด้วยหนึ่งบรรทัดบอกว่าแคชหมดอายุแล้ว เทิร์นนี้ถูกคิดเงินเป็นการส่งซ้ำเต็มจำนวน และหลังจากพักไปเกินหนึ่งชั่วโมง ทางที่ถูกกว่าคือ `/clear` → `/s-continue` ข้อความนี้ไปถึง remote client ได้จริง เพราะคำตอบของ Claude ถูกส่งต่อเสมอ แม้ข้อความจาก hook จะไม่ถูกส่งก็ตาม

ในโหมด `block` prompt จะถูกปฏิเสธหนึ่งครั้งพร้อมข้อความด้านล่าง ส่ง prompt เดิมซ้ำอีกครั้งแล้วมันจะผ่านไป ใช้โหมดนี้ใน terminal ในเครื่องเมื่อคุณต้องการให้หยุดแบบเข้มงวด

```
🚨 Cache expired (68m 23s idle)

แคชของ prompt หมดอายุแล้ว การทำงานต่อจะส่งคอนเทกซ์ทั้งหมดซ้ำ
ต้นทุนอาจเพิ่มขึ้นอย่างมาก

👉 /context — ตรวจสอบการใช้คอนเทกซ์ปัจจุบันก่อนตัดสินใจ
👉 /clear → /s-continue — รีเซ็ต แล้วกู้คืนคอนเทกซ์เดิม (แนะนำ ถูกที่สุด)
👉 ส่งซ้ำ — ทำงานต่อตามสภาพ (เสียค่าใช้จ่าย re-cache เต็มจำนวน)
```

**Background agents ไม่ถูกบล็อกเลย** มีแต่ prompt ที่มนุษย์พิมพ์เองเท่านั้นที่จะได้รับการตรวจสอบนี้ รายงานความสำเร็จจาก background agents และ task ต่างๆ — ซึ่งตอนนี้มักจะมาถึงหลังจากเริ่มทำงานไปแล้วมากกว่าหนึ่งชั่วโมงเป็นเรื่องปกติ — จะผ่านไปโดยตรง ผลลัพธ์ของ agent ที่ทำงานยาวนานจะไม่มีวันถูกกักไว้หรือสูญหาย

## ⚖️ ปลั๊กอินนี้มีค่าใช้จ่ายอะไรสำหรับคุณ

ปลั๊กอินฉีดคอนเทกซ์เมื่อเริ่ม session นี่คือจำนวนที่แน่นอน:

| การฉีด | เมื่อไร | โทเค็น | วัตถุประสงค์ |
| ------- | ------- | ------- | ------------- |
| Session Architect | SessionStart (ครั้งเดียว) | ~1,100 | กลยุทธ์การมอบหมาย SubTask + กฎ Concise Mode |
| คอนเทกซ์ Git (ถ้า git-lite เปิดใช้งาน) | SessionStart (ครั้งเดียว) | ~280 | แทนที่ ~2,200 tok คำสั่ง git ดั้งเดิมของ CC |
| คำเตือนแคชหมดอายุ | เมื่อไม่ได้ใช้งาน > 59 นาที (ครั้งเดียว) | ~200 | ชี้ให้เห็นการส่งซ้ำที่แพง แสดงทางที่ถูกกว่า |
| Status line | ทุก API call | 0 | แสดงใน status bar ของ terminal ไม่ใช่คอนเทกซ์การสนทนา |

**Overhead สุทธิต่อ session: ~1,400 โทเค็น (ครั้งเดียว cache หลังจาก call แรก)**

ที่ราคา Opus ($0.50/MTok อ่านแคช) นั่นคือ **$0.0007 ต่อ API call** — น้อยกว่าหนึ่งในสิบของเซนต์ ใน session 100-call: $0.07

ถ้า git-lite เปิดใช้งาน ปลั๊กอิน **ประหยัด** ~1,920 โทเค็นต่อ session (แทนที่ 2,200 ด้วย 280) ผลลัพธ์สุทธิเป็นลบ — ปลั๊กอินใช้น้อยกว่าที่มันลบออก

**สำหรับผู้ใช้ API แบบจ่ายตามการใช้งาน:** ที่การใช้จ่าย $3,000/เดือน overhead ของปลั๊กอินต่ำกว่า $2/เดือน การส่งซ้ำ $9 ที่ถูกบล็อกหนึ่งครั้งต่อสัปดาห์ (การป้องกันแคชหมดอายุ) จ่ายค่า overhead หนึ่งปีในการจับครั้งเดียว

## 💡 เคล็ดลับ

### เข้าใจแคชแล้วคุณจะเห็นว่าเงินไปอยู่ที่ไหน

- **1 prompt ≠ 1 API call** ทุกครั้งที่ Claude เรียก Grep, Read หรือ Edit คอนเทกซ์ทั้งหมดถูกส่งซ้ำ Prompt หนึ่งรายการสามารถกระตุ้น API calls 10+ รายการได้อย่างง่ายดาย เขียน prompt ที่ชัดเจนเพื่อลด tool calls ที่ไม่จำเป็นและลดต้นทุน
- **ตัวจับเวลาแคชรีเซ็ตจาก API call ล่าสุด ไม่ใช่ prompt ล่าสุดของคุณ** ทำงานต่อและแคชจะไม่หมดอายุ อันตรายคือการจากไป Token Guardian บอกคุณว่ามันเกิดขึ้นเมื่อไร และในโหมด `block` จะหยุด prompt ไว้หนึ่งครั้งเพื่อให้คุณเลือก: รีเซ็ตคอนเทกซ์หรือดำเนินต่อไปตามสภาพ
- **ขนาดคอนเทกซ์ = ตัวคูณต้นทุน** API call เดียวกันที่ 200K เทียบกับ 800K มีค่าใช้จ่ายมากกว่า 4x เมื่อ status line [CTX] เกิน 35% (🟡) นั่นคือสัญญาณให้มอบหมายให้ SubTask มากขึ้น

### นิสัยที่ลดต้นทุน

- **รักษา CLAUDE.md ให้กะทัดรัด** มันถูกโหลดเข้าสู่ system prompt ทุก API call ทุกบรรทัดเสียเงิน
- **มอบหมายงานหนักให้ SubTask** การสร้างโค้ด การแก้ไขหลายไฟล์ การรันทดสอบไม่ควรอยู่ใน Main SubTask มีคอนเทกซ์เล็กกว่าและระดับแคชที่ถูกกว่า
- **จากไป 1+ ชั่วโมง?** `/clear` → กลับมา → `/s-continue` คอนเทกซ์กู้คืนที่ $0
- **[5H] เกิน 70% (🟡)?** ชะลอลง สลับไปทำงานตรวจสอบที่เบาหรือเพิ่มการมอบหมาย SubTask เพื่อลดจำนวน API call ของ Main
- **ใช้ `/btw` สำหรับคำถามข้างเคียง** มันไม่เข้าประวัติการสนทนา ดังนั้นคอนเทกซ์ของคุณจึงกะทัดรัด

### API แบบจ่ายตามการใช้งาน: นิสัยที่สำคัญที่สุด

ทุกอย่างข้างต้นใช้ได้ บวกกับลำดับความสำคัญเฉพาะ API เหล่านี้:

- **ดู [CTX] เหมือนมาตรความเร็ว** Rate limit จะไม่หยุดคุณ — แต่คอนเทกซ์ที่ 500K+ หมายความว่าทุก API call มีค่าใช้จ่าย 2-3x เท่าที่ควร `/clear` → `/s-continue` ฟรีและรีเซ็ตตัวคูณต้นทุนของคุณกลับไปที่เส้นฐาน
- **รัน `/usage-view` รายสัปดาห์** ผู้ใช้ Max Plan มีช่วงเวลา "อุ๊ย" ตามธรรมชาติเมื่อโดน rate limit คุณไม่มี — ต้นทุนพุ่งขึ้นอย่างเงียบๆ แดชบอร์ดคือระบบเตือนภัยล่วงหน้าของคุณ
- **ตั้งงบประมาณรายวันในใจ** ถ้าไม่มีเพดาน วัน $200 เกิดขึ้นโดยไม่รู้ตัว ตัวบ่งชี้ RUN ของ status line ทำให้ต้นทุนต่อเทิร์นมองเห็นได้ ถ้าเทิร์นเดียวเกิน $1 (🔴) คอนเทกซ์ของคุณใหญ่เกินไป
